AI 駆動開発では、生成されるコードを人がすべてレビューするのは難しくなります。代わりに、AI が動く環境（ハーネス）を整えることで品質を保つ考え方と、その実例をまとめます。

## レビューが追いつかない

AI エージェントにコードを書かせると、人が書くよりはるかに多くのコードが短時間で出てきます。1行ずつ読んで確かめるやり方では、すぐにレビューが追いつかなくなります。

そこで注目されているのが**ハーネスエンジニアリング**です。「Agent = Model + Harness」という言い方があるように、AI エージェントはモデルと、その外側にあるハーネスでできています。ハーネスエンジニアリングは、このモデル以外の部分、つまり守るべきルール、使える道具、結果を確かめる仕組みを設計することです。

似た言葉との関係は、次のように整理できます。

- **プロンプトエンジニアリング**：1回ごとの指示を工夫する
- **コンテキストエンジニアリング**：AI に渡す情報全体を工夫する
- **ハーネスエンジニアリング**：AI が動く環境全体を設計する

後ろのものほど範囲が広く、前のものを含みます。同じモデルでも、ハーネスの出来によって成果は大きく変わります。モデルはそのままでハーネスだけを変え、ベンチマークの正答率が 38% から 60% に上がったという報告もあります。

## 中身は多少 AI 任せでもよいと考えている

個人的には、**テストがある程度正しければ、実装の中身は多少 AI 任せでもよい**と考えています。

すべての行を人が読むより、「何が満たされていれば正しいか」をテストとして人が決め、実装はそれを満たすように AI が書くほうが、量が増えても品質を保ちやすいからです。人が責任を持つ場所を、実装からテストと仕様に移すイメージです。

（テストコードのレビューだけでも大変ではありますが…笑）

## それでもルールは把握しておく

ただし、中身を任せることと、何も知らないことは違います。次のような場面では、コードがどんなルールで書かれているかを人が知っている必要があります。

- **AI が動かなくなったとき**：障害や制限で AI が使えない日にも、人が読んで直せる状態でなければいけません
- **調査するとき**：不具合の原因を追うとき、「このディレクトリには何が置かれるはずか」「なぜこう書くのか」が分からないと、どこから疑えばよいか判断できません

ここでハーネスが役に立ちます。AI に守らせるために書いたルールは、そのまま**人が読むための説明書**にもなります。AI が迷わないように書いたものは、あとから参加した人やしばらく離れていた自分にとっても分かりやすいものです。

## 前提のハーネスと後付けのハーネス

ハーネスには2種類あると考えています。

|                | 前提のハーネス                  | 後付けのハーネス                   |
| -------------- | ------------------------------- | ---------------------------------- |
| 効くタイミング | 書く前・書いている最中          | 書いたあと                         |
| 役割           | 正しい書き方を伝える            | 間違いを検出する                   |
| 例             | ルール、手順書（Skill）、設計書 | Lint、テスト、型・スキーマ検証、CI |
| 強さ           | お願い（守られないことがある）  | 強制（通らなければ先に進めない）   |

**前提のハーネス**は、AI が書き始める前に「このプロジェクトではこう書く」を伝えるものです。ただし AI が必ず守るとは限りません。

**後付けのハーネス**は、書かれたものを機械的に確かめるものです。守られなかったルールを確実に拾えますが、機械で判定できることしか確かめられません。

どちらか一方では足りず、組み合わせて使います。

この2つは、一般には**フィードフォワード**（前提）と**フィードバック**（後付け）と呼ばれています。もとは制御工学の言葉で、Birgitta Böckeler さんの記事「Harness engineering for coding agent users」では、それぞれ Guides と Sensors として整理されています。

ハーネスの導入を3段階で説明する考え方もあります。ルールを文章にする段階、Linter やテストで自動的に縛る段階、ログを見ながら改善し続ける段階です。最初の2つがそれぞれフィードフォワードとフィードバックに、最後の1つが後で述べる「ハーネスを育てる」ことにあたります。

## このポートフォリオでの実例

私のポートフォリオ（[tora29.net](https://tora29.net)、[ソースコード](https://github.com/Tora29/my-portfolio)）も、Claude Code を使って開発しています。

### 前提のハーネス

- **CLAUDE.md**：プロジェクトの概要、コマンド、作業時の注意を書いています。AI が最初に読む入口です
- **ルール（`.claude/rules/`）**：ディレクトリ構造、コメント、テスト、アクセシビリティ、Git の運用など、テーマごとにファイルを分けています
- **Skill**：「フォーマット → Lint → 単体テスト → ビルド → E2E → 静的解析を順に実行して報告する」「ブランチ作成から PR 作成、マージ後の片付けまでを行う」といった、繰り返す手順を定義しています

ルールには「何をするか」だけでなく「なぜそうするか」を書くようにしています。たとえばテストのルールには「テストデータは実データに依存させない（コンテンツを更新してもテストが壊れないように）」と理由まで書いています。理由があると、AI はルールに書かれていない場面でも近い判断をしやすくなり、人が読んだときにもルールの意図が伝わります。

### 後付けのハーネス

- **スキーマ検証**：このポートフォリオでは、記事や作品に「使った技術」を付け、技術ごとに一覧できるようにしています。ここで同じ技術が「TypeScript」と「TS」のように別の書き方をされると、別の技術として扱われ、一覧が分かれてしまいます。見た目では気づきにくい間違いなので、技術名はあらかじめ登録した一覧から選ぶ決まりにし、一覧にない名前が書かれたらサイトの生成（ビルド）を失敗させています
- **テスト**：ロジックが集中する部分（技術ごとの集計や、GitHub からの Activity 生成）は単体テストを必須にし、ページは E2E テストで主要な導線を確かめています
- **CI**：PR ごとにフォーマット、Lint、テスト、ビルド、E2E、Semgrep による静的解析を実行します

ローカルでは、上の Skill で同じチェックを AI 自身に実行させています。AI が「できました」と言う前に、壊れていないことを自分で確かめさせるためです。

## ハーネスは育てるもの

ハーネスは最初から完成するものではなく、使いながら直していきます。

直すときは、次のように考えています。

- **後付けのハーネスで何度も同じ指摘を受ける**なら、前提のハーネスにルールとして書く（最初から正しく書かせる）
- **前提のハーネスに書いても守られない**なら、機械的に判定できる形にして後付けのハーネスへ移す（確実に止める）
- **前提のハーネスが効いていない**なら、読み込まれる仕組みそのものを見直す

先の Böckeler さんの記事でも、同じ問題が何度も起きたらフィードフォワードとフィードバックを改善し、再発しにくくすることが人の役割だとされています。

## まとめ

- AI 駆動開発では、すべてをレビューする代わりに、正しさをテストで担保する
- ただし、コードがどんなルールで書かれているかは人も把握しておく。ハーネスはそのための説明書になる
- ハーネスには、書く前に伝える「前提」と、書いたあとに確かめる「後付け」がある。両方を組み合わせ、使いながら育てる
