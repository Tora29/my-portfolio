# コメントルール

コードを読むだけでは分からない「なぜ」を残す。

## 基本方針

- コメントは日本語で書く
- 「何をしているか」はコードで表し、コメントには**理由・前提・注意点**を書く
- 設計書を参照してよいが、参照だけで済ませない（設計書を読めない人にも伝わる説明を添える）
- コードを変更したら、関係するコメントも同時に直す（古いコメントを残さない）

## 書く場所

### ファイルの先頭

`src/lib/`・`scripts/`・`src/content.config.ts` のように処理を持つファイルには、先頭に JSDoc で次を書く。

- そのファイルの役割（1〜2文）
- 他のファイルとの分担（例：集計は `build-graph.ts`、読み込みは `load-graph.ts`）
- 実行されるタイミングの制約（例：ビルド時のみ。ブラウザ向けのコードから import しない）
- 関係する設計書

```ts
/**
 * Engineering Graph の集計
 *
 * Works / Notes / Career / Activity に付けられた Tech をビルド時に逆引き・集計する。
 * このファイルは Astro に依存しない純粋な関数だけを置く（単体テストの対象）。
 * Content Collections からの読み込みは load-graph.ts が行う。
 *
 * 設計：.users/design/engineering-graph.md §5〜§7
 */
```

### 関数

export する関数と、処理が複数の段階に分かれる関数には JSDoc を書く。

- 何を受け取り、何を返すか（特に「見つからないときは undefined」のような境界の扱い）
- 呼び出す側が守るべき前提（例：循環がないことを確認してから呼ぶ）
- 処理が段階に分かれる場合は、段階を番号付きで並べ、本体の該当箇所にも同じ番号を付ける

### 判断の理由

次のような、読み手が「なぜこうしたのか」と疑問に思う箇所には必ず書く。

| 箇所 | 例 |
| --- | --- |
| あえて除外・制限している | 関連 Tech から上位・下位を除く（AWS の関連に Lambda が常に出ても情報にならないため） |
| 並び順・同点時の扱い | 同数のときは tech.yml の順（ビルドごとに並びが変わらないように） |
| エラーにしない・警告に留める | 未使用の Tech は警告のみ（先に定義しておくことがあるため） |
| ライブラリの挙動への対処 | 記述順を order として持たせる（getCollection が記述順を保証しないため） |
| 定数の値 | 関連 Tech の上限を 10 件にする理由 |
| 一見不要に見える処理 | 種類と id を組み合わせたキー（id は種類ごとに独立しているため） |

### 型・スキーマ

- 型のフィールドには、名前だけでは区別しにくい意味を書く（例：`direct` と `total` の違い）
- スキーマの項目には、画面のどこで使うか・なぜ必須か・値の制約を書く（例：`先頭6個が常に表示されるため、重要なものから並べる`）

## 書かないもの

- コードをそのまま言い換えただけのコメント（例：`// id を返す`）
- 作業の経緯・変更履歴・日付（Git の履歴とPRに残す）
- コメントアウトしたコード（不要なら消す）
- TODO の放置。書く場合は、何をすれば消せるかまで書く

## テスト

- テスト名は日本語で、何を確かめるかを書く（`testing.md`）。テスト名で意図が伝わる場合、コメントは不要
- テストデータの意図が分かりにくい場合のみ、組み立ての意味をコメントで補う
