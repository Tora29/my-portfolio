# 書き手の口調（Zenn の記事）

Zenn の記事は、書き手本人の口調で書く。推敲でこの口調を消さない。ユーザーに「この風味にして」と頼まれたときは、この口調に寄せる。

## 使う場所

- Zenn の記事（`articles/`）だけで使う
- PR のタイトルと本文、作品・職歴の文章、`data/profile.yml` には使わない。採用担当も読むポートフォリオに出るため、落ち着いた説明のままにする

## 特徴

| 特徴 | 例 |
| --- | --- |
| ベースは敬体。仕組みや手順の説明は崩さない | 「確認用 PR の本文には、まだ公開していない Activity が一覧で載ります。」 |
| 章の頭や締めに、くだけた一言（話し言葉・独り言）を入れる | 「ありきたりなものはつまらんなぁ、、と思った今日この頃。」 |
| 「、、」でためらい・照れ・余韻を出す（「…」も使う） | 「ポートフォリオがほしい、、！」 |
| 「！」で軽く言い切る | 「開発さえ続けていれば勝手に育つ、、はずです！」 |
| 自分の性格や本音を、動機や理由として書く | 「しかも自分の性格上、絶対に更新をサボると思いました。」 |
| 照れや本音はカッコで添え、「笑」で結ぶ | 「（テストコードのレビューだけでも大変ではありますが…笑）」 |
| タイトルは話し言葉にし、「〜してみた」「〜な話」で結ぶ | 「勝手に育つポートフォリオを構築してみた」「AI のために書いたハーネスが、人間の説明書にもなっていた話」 |
| 弱点や課題も隠さずに書く | 「『具体的に何をどれだけできるか』は逆に伝わりにくくなっています。」 |

表記：「サボる」はカタカナで書く。

## 入れ方

- くだけた一言は、1つの章に1〜2か所までにする。コードの解説や手順の途中には入れない
- 事実を変えない。仕組みと合わない冗談を書かない（例：件数に連動する表示を「サボると減る」と書く）
- 同じ冗談や言い回しを、1本の記事の中で繰り返さない
- 書き手の気持ち・性格・理由を想像で足さない。足した文は報告の「想像で足した文」に挙げ、本人に確かめる
- 予定や断定を冗談で弱めるとき（「取り組んでいきます、、たぶん」）は、読み手にどう見えるかを添えて確かめる

## 実例

本人が書いた文、または本人が手を入れて採った文。

- 「ポートフォリオがほしい、、！が、ありきたりなものはつまらんなぁ、、と思った今日この頃。」（`articles/static-first-portfolio.md`）
- 「しかも自分の性格上、絶対に更新をサボると思いました。」（同上）
- 「（ポートフォリオで生活感まで出すわけにはいかないので、、笑）」（同上）
- 「サボり癖のある自分でも、開発さえ続けていれば勝手に育つ、、はずです！」（同上）
- 「（テストコードのレビューだけでも大変ではありますが…笑）」（`articles/harness-as-ai-manual.md`）
- 記事の冒頭に、自分と AI の掛け合いを置いて困りごとを見せる（`articles/testglass-test-review.md`）
  ```text
  ワイ「ほなこの仕様から導けるテストコード書いてクレメンス。」
  AI 「できたで！（すごい量のテストコード）」
  ワイ「、、アウトプット多すぎィ！！」
  ```
- 「という感じで AI にテストを書かせると、その大量のアウトプットを前にレビューが追いつかなくなります。」（同上。掛け合いから本文へのつなぎ）
- 「（ほかの言語にも対応したい、、！意欲はあります）」（同上。今後の展望を、約束ではなく意欲として本音で添える）

## 使わない言い方

本人が「この言い方はしない」と言ったものを書く。

- （まだない）

## 育て方

- ユーザーが推敲の結果を自分で書き換えたら、その文を「実例」に足すか聞く。足すのは了承を得てから
- ユーザーが言い方を断ったら、「使わない言い方」に足すか聞く
- 特徴の表と食い違う実例が増えたら、表の見直しを提案する
