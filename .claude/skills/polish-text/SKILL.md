# polish-text

AI が書いた日本語にありがちな読みにくさ（誰が何をしたのか分からない、比喩でぼかす、飾りが多い）を直す。言っていることは変えず、言い方だけを直す。

Zenn の記事は書き手本人の口調で書く。口調の特徴・入れ方・実例は `voice.md` にまとめている。推敲で口調を消さない。

## 対象

- `articles/` の記事
- PR のタイトルと本文（Activity としてサイトに公開される。`.claude/rules/git-workflow.md`）
- `content/` の作品・職歴の文章、`data/profile.yml` の紹介文

## いちばん大事なこと：意味を変えない

直す前に次の4つを確かめ、直したあとも同じに保つ。下の「観点」は、この4つを変えない範囲でだけ使う。

1. **主張**：何を言っているか。論点を別のものにすり替えない
2. **比重**：何を重く、何を軽く扱っているか。否定していたものを並列にしない
3. **言い切りの強さ**：断定は断定のまま、推量は推量のまま。弱めも強めもしない
4. **文の働き**：評価・説明・依頼・予定・感想の区別。評価の文を目標の文に変えない

元の文にない主語・条件・理由・数値を足さない。省かれた語を補うのは、前後の文にその語が書かれているときだけにする。

## 手順

1. 文章全体を読み、文書の立場を1つ決める
   - **説明**：事実・考え・結果を伝える（記事、PR の本文、作品の説明）
   - **勧め**：読み手に何かを勧める（読者への助言）
   - **決まり**：守ることや手順を伝える（ルール、手順書）
   - Zenn の記事なら `voice.md` を読む
2. 下の観点に沿って、直す箇所を探す
3. このリポジトリの仕組みを説明している文は、実装と照らす（「実装と照らす」）
4. 直す箇所を「報告の形」で示す。この時点ではファイルを書き換えない
5. ユーザーが採ったものだけを反映する
6. ユーザーが自分で書き換えた文があれば、`voice.md` の「育て方」に沿って実例に足すか聞く

## 観点

### 文末をそろえる

- 立場に合わない文末だけを直す（例：説明の記事に「〜しましょう」が1文だけ混ざっている）
- 説明の文で、敬体（です・ます）と常体（だ・である）を混ぜない
- Zenn の記事で、`voice.md` の口調として入れたくだけた一言は、混ざっているとみなさない
- 文末がすでにそろっていれば変えない
- 説明の記事で、最後の1文だけを「〜してみてください」で結ぶ形は、混ざっているとみなさない

### 誰が何をしたかが分かるようにする

- 主語と述語がかみ合っていない文を直す
- 「これ」「それ」「両者」が何を指すか分かりにくいとき、前後から指す先が分かる場合だけ名詞に戻す。分からなければ直さずユーザーに聞く

### 道具や概念に意志を持たせない

- 道具や概念が考えたり望んだりしているように書いた文を、人や仕組みの動きとして書き直す
  - 例：「テストが品質を守ってくれる」→「テストで品質を確かめる」
- 仕組みの働きを述べる文（「このコマンドはログを集める」）は直さない
- 直すときに、元の文にない条件（「〜を使えば」）や可能（「〜できる」）を足さない

### 比喩の動詞をふだんの言葉にする

- 「壊れる・倒す・効く・刺さる・溶かす・潰す」などが比喩として使われているとき、意味の広さが同じふだんの言葉に言い換える
  - 例：「バグを潰す」→「バグを直す」、「工数が溶ける」→「工数が無駄になる」
- 言葉が持っていた含み（「ようやく」の待った感じ、「うっかり」の不注意）は、別の言葉で残す
- 「骨が折れる」「手を焼く」のような、ふだんの日本語で定着した慣用句は直さない
- 機械やデータが文字どおり壊れる話は直さない

### 予告だけの文をまとめる

- 「注目すべき点が2つあります。」のように中身のない文は、続く文と1文にまとめる。予告が持っていた重み（「注目すべき」）は述語に残す
- まとめると意味が変わる場合は残す

### 飾りを減らす

- **太字**：本当に強調したい語だけにする。1段落に何か所もあれば減らす
- **箇条書き**：理由や流れでつながる内容は文にする。並べて比べるものは箇条書きや表のまま残す。文にすると同じ文末が3つ以上続く場合も、箇条書きのまま残す
- **「A ではなく B」**：誰も言っていない A をわざわざ否定しているなら、B だけを言う
- **文末のコロン**（「理由は次のとおり：」）と**ダッシュ**（——）は使わない。ダッシュを外して前後を1文につなぐと理由や条件のかかり方が変わる場合は、2文に分ける
- **絵文字**は本文で使わない（Zenn の frontmatter の `emoji` は対象外）
- **カッコ**：前の語を言い換えただけで、情報の増えないものを削る
- Zenn の記事の「、、」「笑」「！」と、本音を添えるカッコは、飾りとみなさない（`voice.md`）

### 文を長くしすぎない

- 1文が長い（目安は60字を超える、または読点が3つ以上）ときは分ける
- 分けると理由や条件のかかる範囲が変わる場合は分けない

## 口調に寄せる（頼まれたとき）

ユーザーに「この風味にして」「自分の口調にして」と頼まれたときだけ行う。Zenn の記事以外では行わない。

- `voice.md` の「特徴」と「実例」に寄せ、「入れ方」を守る
- 上の「意味を変えない」4つは、口調に寄せるときも守る
- 想像で足した文（書き手の気持ち・性格・理由）は、報告の「想像で足した文」に必ず挙げる

## 実装と照らす

記事や PR の本文がこのリポジトリの仕組みを説明しているときは、該当するコードやワークフローを読んで照らす。

- 食い違い（例：「翌日には公開される」が、実装では確認用 PR に入るだけ）は「確かめたい点」に挙げる
- 言い方の推敲とは分け、勝手に直さない

## Zenn の記事で見るところ

- 1回の改行も、改行として表示される。段落を分けたいなら空行を入れる
- コードブロックの言語が中身と合っているか（例：ワークフローの `run:` の中身は `yaml` ではなく `bash`）
- 画面の表示を「」で引くときは、実際に表示される文言と合っているか

## 直さないもの

このリポジトリの書き方に合わせ、次のものは直さない。

- 和文と英数字のあいだの半角空白（「Claude Code を使って」「AI 駆動開発」）。既存のコンテンツや PR と表記をそろえるため
- 理由や条件を添えるカッコ（「articles/ に置く（Zenn がリポジトリ直下しか読まないため）」）
- コード・コマンド・ファイル名・引用・参考文献
- 見出しの順や章立て。構成の見直しは頼まれたときだけ行う
- Zenn の記事の口調（`voice.md`）

## 報告の形

```text
立場：説明（記事）

| # | 元の文 | 直した文 | 理由 |
| --- | --- | --- | --- |
| 1 | バグを潰すために… | バグを直すために… | 比喩の動詞をふだんの言葉にした |

確かめたい点
- 3段落目の「これ」が、前の段落の設定ファイルを指すのか、コマンドを指すのか分からない

想像で足した文（口調に寄せたときだけ）
| 場所 | 足した文 |
| --- | --- |
| 自動で公開する章 | そして私は確実に忘れます。 |
```

- 直す箇所がなければ「直す箇所はありません」と伝える
- 立場が決めきれない、指す先が分からないなど、本人に聞かないと直せない点は「確かめたい点」に挙げ、勝手に直さない
